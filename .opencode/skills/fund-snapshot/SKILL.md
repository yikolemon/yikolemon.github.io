# 基金快照

把「一次统计」变成 `_data/fund/snapshots/YYYY-MM-DD.json` 里的一个文件。

页面是 `repo/fund.html`（地址 `/fund/`），**只读数据、自己算派生数字**。
工作是：**把持仓成本和市值抄准，把 id 对齐，并保留累计已实现收益**。

下面所有路径都相对 `repo/`，命令都在 `repo/` 里跑。

## 铁律

0. **先明确任务，不擅自投资分析** —— 用户要“梳理数据 / 更新收益记录”时，直接整理并更新；不要主动输出配置、加仓、止损等投资建议。
1. **每只持仓只写两个数字** —— `invested`（剩余持仓成本）和 `value`（当前市值）。
   持仓收益 / 收益率 / 占比 / 变化 / 份额**一律不写**，页面自己算。卖出和现金分红的累计已实现收益单独写入快照的 `realized` 对象。
2. **只新建，不修改** —— 一次统计 = 一个新文件。**永远不要回头改旧快照**，
   否则「上一次的数字」就变了，页面上整列「变化」跟着一起错。
3. **`id` 是永久主键** —— 写进 `funds.json` 就不要再改。旧基金复用原 id，新基金先补档案；不要靠显示名称匹配。校验工具和页面会提示未知 id，但未知持仓仍不会进入合计，必须先修正。
4. **口径固定，别混**：`invested` 是剩余持仓成本，`value` 是 App 显示的资产金额；默认不拆在途。累计收益需包含 `realized`，详情见下面的「口径」。
5. **不猜** —— 数字对不上、只给了合计、名字认不出，都去问，不要自己圆。

## 数据在哪

```
repo/_data/fund/
├── meta.json               标题 / 币种 / is_placeholder
├── funds.json              基金档案，一只一条，只填一次
└── snapshots/
    └── YYYY-MM-DD.json     一个文件 = 一次统计；日期取文件名，文件里不写 date
```

某次快照的 `holdings` 里**没出现**的基金 = 当时没持有。下次再出现会被标成「新建仓」，
所以清仓的基金不要留空行，直接移除该持仓；基金档案保留，`realized` 中的累计已实现收益也必须保留。

## 工作模式：截图全自动（推荐）

用户把这一期的截图**全部丢给你**，文件名可以带 App 名，也可以是聊天软件生成的哈希名。
2026-11-24 使用的目录是 `D:\Desktop\临时`，后续以用户当次指定目录为准，不硬编码旧桌面路径。
你在**一次会话里跑完整条流水线**，最后让用户去本地页面验收就行：

```
收图 → 读图 → 汇总表 → 交叉验算 → 对齐 id / 补 funds.json → 写快照
→ fund.py check → 本地预览 → 交验收
```

- **渠道优先从文件名或截图内容判**：支付宝 / 天天基金 / 京东金融 → `场外分销`；基金公司自家 App
  （广发基金 / 南方基金 / 天弘基金…）→ `场外直销`；券商（华泰 / 国信 / 中信…）→ `场内`。
  文件名没写 App 时先读截图，结合旧档案识别。只有文件名、画面和旧档案都不能确定时才问，不要仅因哈希文件名就要求重命名。
- **先建汇总表，再动手写**：把所有截图读完，拼一张 `基金 × 渠道 × 成本 × 市值` 表，
  逐格验算过，才进下一步。不要读一只写一只。
- 汇总表里任何一格对不上 / 缺数据 → **攒成一页「待确认」一次性问用户**，
  不要中途反复打断。
- 跑完**只交本地验收**，不主动 push，用户说提交再提交。
- **文字确认与截图同样有效**：App 禁止截图时，接受用户手打金额、收益和成交到账数，不强求截图。已回答的问题不再重复追问。

## 截图怎么读

**每只基金只需两项可计算数据**：通常是持有金额 + 持有收益，或持仓金额 + 持仓成本。
有三项时校验 `持有金额 = 持仓成本 + 持有收益`；缺成本并不代表缺资料。

- **小字先放大再读**：可用 PIL 或 Windows 的 System.Drawing 裁剪、放大 3~5 倍再逐位读；不要因未安装 PIL 就停住
  （第一次初始化没放大，`107.71` / `117.71` 就差点看岔）。
- 页面通常给「持有金额 + 持有收益」，成本 = 金额 − 收益；有「持仓成本」就直接读。
- **不要为可计算的成本追加索要截图**。例如万家直销资产 `1911.67`、持有收益 `-188.33`，直接得到成本 `2100.00`。不能把“累计收益”自动当成“持有收益”，有卖出或分红时两者可能不同。
- **别用「持有收益率」反推投入** —— 收益率口径各家不一。
- 场内按「成本价 × 持股 = 成本、现价 × 持股 = 市值」。
- **代销以平台 App 为准**（支付宝等），基金公司 App 里的「XX-代销」
  可能滞后，只用来确认直销。
- **总资产包含多个渠道时先去重**：如直销资产没有单列，可用公司 App 总资产减其中明确列出的代销资产；收益也使用同一来源对应渠道扣除。支付宝与公司 App 可能存在在途、更新时间差异，不可跨时点强行抹平。
- **合计与单只明细出现分位尾差**：逐只数据为准，注明尾差，不擅自修改某只数字凑合计。2026-11-24 支付宝合计与逐只求和相差 `0.01` 元。

| App | 渠道 | 读数要点 |
| --- | --- | --- |
| 支付宝 / 天天基金 | 场外分销 | 列表页「持有金额 / 持有收益」；成本 = 金额 − 收益 |
| 广发基金 / 南方基金 / 万家基金 / 建信基金… | 场外直销 | 读直销资产 + 持有收益；成本可计算；注意总资产可能还含代销 |
| 券商（华泰 / 国信 / 中信…） | 场内 | 成本价 × 持股、现价 × 持股 |

- **在途口径已于 2026-11-24 明确**：用户要求“显示多少就记多少”，默认直接记录资产金额，不扣已包含在其中的在途资金，也不把交易列表的待确认金额再额外加一遍。**不要再索要在途分配明细，不要按收益率反推在途。**只有用户明确更改口径时才另行处理，并写入当期备注。
- **旧口径保留**：2026-10-17 曾排除部分确认中申购；不回改旧快照，在新快照备注说明差异即可。
- **保持同一批截图的统计时点**：凌晨持仓与午后新增扣款不能混算。补充交易截图用于核对，不自动把更晚交易补进更早资产。
- **现金分红 / 卖出**：剩余持仓成本与累计已实现收益分开记录，见「口径」；金额不明确时询问用户，不猜。
- **日期口径**：场外 QDII 净值滞后（10-15/10-16 净值），场内按统计当日收盘，
  同一天混记允许，写进 `note` 即可。

## 口径

页面里的「口径说明」和这里是同一套，**改一边要改另一边**。当前的约定：

- `invested` = **剩余持仓成本**，以 App 成本口径为准；卖出时扣除卖出部分成本，不是历史累计买入金额
- `value` = App 显示的资产金额（场内按统计时点市价，场外按最新可见资产金额，可能含在途；保留净值滞后说明）
- 持仓收益 = `市值 − 剩余持仓成本`
- `realized` = `{ "基金id": 累计已实现收益 }`；卖出净到账减卖出部分成本，现金分红也计入，可为负数；这是累计额，不是单期增量
- 累计收益 = 持仓收益 + 已实现收益。清仓后从 `holdings` 移除，但 `realized` 中必须保留，后续快照继续携带；`fund.py new` 会自动复制
- 历史快照无 `realized` 时按 0 计算，不回改旧快照。卖出到账现金不计入基金市值
- 只展示持仓收益率（持仓收益 / 持仓成本）；没有完整资金流水，不计算累计收益率或年化收益率

### 卖出与分红

不要把卖出后的市值设为 0 却保留原持仓成本，否则会产生虚假亏损。也不要只在备注中记录已实现收益。

| 情况 | 为什么会假亏 | 怎么办 |
| --- | --- | --- |
| **现金分红** | 分红后市值下降 | 将实际分红加入 `realized`，不要同时冲减成本而重复计收益 |
| **卖出 / 赎回** | 只减市值、不减成本会制造假亏损 | 扣除对应持仓成本，净到账减卖出成本加入 `realized`；全部清仓移除持仓 |

2026-11-24 首次记录清仓：159632 成本 1029.90 元、净到账 1093.01 元，累计已实现收益 63.11 元。部分卖出需要实际卖出部分的成本，不要用整个持仓成本计算。

### 最少需要补问什么

- 普通持仓：有“金额 + 持有收益”即可，不需要另问成本和在途。
- 清仓：确认卖出净到账及成本；历史成本可靠且用户同意沿用时直接沿用。不要仅因券商有现金就假定全部是卖出所得，用户确认后才采用。
- 部分卖出：需要卖出部分对应成本及净到账，或可信的 App 已实现收益；不能拿整个账户成本计算。
- 现金分红：只有实际发生才记，不因页面显示“现金分红”设置就假定已经分红。
- 某平台“持有收益”和“累计收益”不同，不足以证明用户赎回过；不要反复质疑用户已经确认的“没有赎回”，更不能自行把差额加进 `realized`。
- 只把无法从现有截图、文字或旧档案确定的问题汇总一次询问，不要求用户再次提供已经足够计算的数据。

## funds.json 字段

| 字段 | 必填 | 取值 / 说明 |
| --- | --- | --- |
| `id` | ✓ | 永久主键。小写 ASCII，`公司拼音_标的`，如 `tianhong_nasdaq100`、`morgan_sp500`。只用小写字母 / 数字 / 下划线，全局唯一 |
| `name` | ✓ | 全称，尽量和 App 里显示的一致 |
| `code` | | 基金代码。**场内的 6 位代码一定要填**（如 `513100`）；场外没有就写空串 `""` |
| `venue` | ✓ | 只有 `场内` / `场外` |
| `channel` | ✓ | 只有 `场内` / `场外直销` / `场外分销` —— **页面「按渠道」维度用的就是它** |
| `platform` | | 自由文本：`券商·华泰` / `支付宝` / `天天基金` / `富国基金官网` |
| `tracking` | | 跟踪标的：`纳斯达克100` / `标普500` / `沪深300`；主动基金写策略 |
| `category` | | `ETF` / `QDII指数` / `指数基金` / `主动基金` / `债券` |

### venue / channel 怎么判

| 在哪买卖 | `venue` | `channel` |
| --- | --- | --- |
| 券商 App（华泰 / 中信…） | `场内` | `场内` |
| 基金公司官网 / 自家 App | `场外` | `场外直销` |
| 支付宝 / 天天基金 / 蛋卷等第三方 | `场外` | `场外分销` |

`channel` 是最常漏的字段（`fund-data-real-backup-2026-10-17.json` 里十只全缺），
漏了页面会把这些基金归到「未分类」，`fund.py check` 会提醒。

## 快照文件长什么样

```json
{
  "note": "按 App 显示资产记录，包含页面已计入的在途；场内已清仓，净到账不计入基金市值。",
  "realized": {
    "huaan_nasdaq100_etf": 63.11
  },
  "holdings": [
    { "id": "tianhong_nasdaq100", "invested": 5200.00, "value": 5605.58 }
  ]
}
```

- `note` 可空，写一句当天的情况（「补上券商账户」「卖出 300ETF 一半」）
- `holdings` **只列当时有持仓的基金**
- `realized` **累计保存**：没有新卖出也要从上期继续携带，不置零、不漏项；有新交易只把本次新增已实现收益加到原累计值上。不要把 App 全历史累计额当增量再加一次。
- **不要写 `date`** —— 日期取文件名，写了 `check` 会提醒删掉
- 金额用数字，不要用字符串；保留两位小数

## 流程（一次会话跑完，不中途打断用户）

1. **收图** —— 优先读取用户指定目录，按截图统计时点整理；
   从文件名和画面判 App → 渠道，建一张「截图清单」。
2. **读图** —— 逐张放大读数，填汇总表（基金 × 渠道 × 成本 × 市值）。
3. **验算** —— 每只 `金额 = 成本 + 收益`；同渠道合计 vs App 页脚合计。
   对不上 → 攒「待确认」一次性问用户。
4. **对齐 id** —— 每只都要能在 `funds.json` 里找到；
   新基金先补档案（venue / channel / tracking / category 全填），再写快照。
   不要随意改旧 id；新基金按命名规则建档后即可加入快照。
5. **写快照** —— `python script/fund.py new <日期>` 用上期做模板，只改
   `invested` / `value`，删掉本次没持有的行，保留并更新 `realized`；同一天只能一份。已存在当天文件时先判断是否是本次尚在核对的草稿，不覆盖历史已验收快照。
6. **校验** —— `python script/fund.py check`，报错先修再往下。
7. **本地预览** —— `bundle exec jekyll build`；检查实际预览端口是否可用，确认 `/fund/` 的三种收益及金额与汇总表一致。当前常用 `http://127.0.0.1:4001/fund/`，但不要未经验证就保证服务仍在运行，详见下面“本地预览注意事项”。
8. **交验收** —— 把汇总表 + 变更摘要发给用户核对；**不主动 push**，
   用户说提交再提交（`git add _data && git commit && git push`）。

## 对账

写完自己加一遍，和 App 里的合计对照：

- 持仓成本 ↔ App 当前持仓成本，或资产金额减持有收益；不能在卖出后对照历史累计买入
- 总市值 ↔ App「总资产」/「持仓市值」
- 持仓收益 = 市值 − 持仓成本
- 已实现收益 = `realized` 中各基金累计额之和
- 累计收益 = 持仓收益 + 已实现收益；本金、卖出到账现金不能当作收益再次加进来

```powershell
python -c "import json;from decimal import Decimal as D;from pathlib import Path;p=max(Path('_data/fund/snapshots').glob('????-??-??.json'));d=json.loads(p.read_text(encoding='utf-8'));i=sum((D(str(h['invested'])) for h in d['holdings']),D(0));v=sum((D(str(h['value'])) for h in d['holdings']),D(0));r=sum((D(str(x)) for x in d.get('realized',{}).values()),D(0));print(p.name);print('cost',i,'value',v,'holding_profit',v-i,'realized',r,'total_profit',v-i+r)"
```

对不上就先别提交，把差异定位到具体哪只基金。

## 输入形态

| 形态 | 怎么做 |
| --- | --- |
| **一批截图（推荐）** | 文件名或画面识别 App，全部走「截图全自动」流水线 |
| **复制粘贴的文字** | 直接解析；注意别把「持有收益」当「累计投入」 |
| **手打清单** | 先 `fund.py new <日期>` 出模板再填，省得对不齐 |
| **只给合计** | 先看能否结合现有明细去重、扣除其他渠道；确实无法拆分时再要单只明细，不能编数据 |

## 常见错误（都是「不报错但数据错」）

| 症状 | 后果 | 谁会发现 |
| --- | --- | --- |
| `id` 拼错 | 那只基金静默消失，总数凭空变小 | `check` + 页面顶部橙条 |
| 漏抄一只 | 少算一只 | `check` 提醒「上次有、这次没写」 |
| `invested` 下降 | 可能部分卖出，也可能抄错 | 核对剩余成本及 `realized`，不能一概认定抄错 |
| 同一天两份文件 | 文件名唯一，不可能 | 新建时就会拒绝 |
| 把「持有收益」当投入 | 收益变负数 | 一眼能看出来 |
| 分红 / 卖出只写备注 | 累计收益漏掉已实现部分 | 写进 `realized`，卖出同步扣除对应持仓成本 |
| 后续遗漏 `realized` | 清仓收益从总收益消失 | `check` 会报错，模板自动携带上期累计值 |
| 重复计算代销持仓 | 市值和投入双倍计算 | 平台为准，公司 App 只补直销 |
| 反复扣在途 | 与用户约定的 App 显示口径不一致 | 不拆在途，不跨时点混入新交易 |
